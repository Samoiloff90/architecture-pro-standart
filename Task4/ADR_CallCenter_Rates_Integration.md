## Контекст и проблема

Целевая аудитория банка «Стандарт» — **пожилые клиенты**, которые предпочитают уточнять условия по телефону. После запуска маркетинговой кампании по депозитам ожидается **резкий рост звонков в кол-центр**. Необходимо обеспечить два типа интеграции:

1. **Банковский кол-центр** — получает актуальные ставки через **REST API** (pull-модель каждые 5 минут).
2. **Партнёрский кол-центр** — не имеет возможности API-вызовов; готов получать ставки в виде **файлов по SFTP**.

Цель: сотрудники обоих кол-центров могут консультировать клиентов по актуальным депозитным ставкам в режиме, близком к реальному времени (задержка не более 15 минут для партнёра).

## Use Cases

### UC-6: Консультация клиента сотрудником банковского кол-центра

**Действующие лица:** Клиент, Сотрудник кол-центра, Система кол-центра банка, Rate Management Service

**Описание потока:**
1. Клиент звонит в кол-центр
2. Сотрудник открывает систему кол-центра
3. Система автоматически (каждые 5 минут) опрашивает API `GET /api/rates/public`
4. Сотрудник видит актуальные ставки по всем депозитам
5. Сотрудник консультирует клиента

### UC-7: Консультация клиента сотрудником партнёрского кол-центра

**Действующие лица:** Клиент, Сотрудник партнёрского кол-центра, Система партнёра, SFTP Server

**Описание потока:**
1. Клиент звонит в партнёрский кол-центр
2. Сотрудник партнёра открывает свою систему
3. Система партнёра (каждые 15 минут) забирает файлы CSV/JSON с SFTP
4. Система импортирует данные в локальную БД
5. Сотрудник видит актуальные ставки
6. Сотрудник консультирует клиента

### UC-8: Обновление ставок в кол-центрах

**Действующие лица:** Сотрудник бэк-офиса, Rate Management Service, Kafka, SFTP Rate Exporter

**Описание потока:**
1. Сотрудник изменяет ставку в Rate Management Service
2. Система публикует событие `RateUpdated` в Kafka
3. Redis-кеш инвалидируется
4. SFTP Rate Exporter получает событие из Kafka
5. Генерируются файлы `rates_YYYYMMDD_HHmmss.csv` и `.json`
6. Файлы загружаются на SFTP-сервер
7. Банковский кол-центр получит обновление при следующем опросе API (до 5 мин)
8. Партнёрский кол-центр получит файл при следующем заборе с SFTP (до 15 мин)

## Функциональные требования

| № | Требование |
|---|------------|
| **F-8** | Public REST API `/api/rates/public` для получения актуальных ставок по всем депозитам |
| **F-9** | API не требует аутентификации клиентов, но защищён API-ключом для систем кол-центров |
| **F-10** | Автоматическая генерация CSV и JSON файлов при изменении ставок |
| **F-11** | Формат CSV: columns = [deposit_name, rate_percent, term_months, min_amount, max_amount, currency] |
| **F-12** | SFTP-сервер для передачи файлов со ставками партнёрскому кол-центру |
| **F-13** | Автоматическая очистка файлов старше 7 дней на SFTP |
| **F-14** | Event-driven архитектура: публикация события `RateUpdated` в Kafka при изменении ставок |

---

## Нефункциональные требования

| № | Требование |
|---|------------|
| **NFR-11** | API `/api/rates/public` должен отвечать за < 500 мс (P95), целевое < 200 мс |
| **NFR-12** | Файлы на SFTP должны обновляться в течение 5 минут после изменения ставки |
| **NFR-13** | Аутентификация банковского кол-центра через API-ключи (Kong API Gateway) |
| **NFR-14** | Аутентификация партнёрского кол-центра через SSH-ключи (public key authentication) |
| **NFR-15** | Rate limiting для API: 100 requests/minute на API-ключ (защита от DDoS) |
| **NFR-16** | IP whitelist для SFTP: доступ только с IP партнёра |
| **NFR-17** | Кеширование ответов API в Redis с TTL = 5 минут |
| **NFR-18** | SFTP Server должен быть в HA режиме (high availability) |

## Архитектурное решение

### Обзор

Выбрана **event-driven архитектура** с двумя каналами интеграции:
- **Синхронный канал (REST API)** для банковского кол-центра
- **Асинхронный канал (SFTP + файлы)** для партнёрского кол-центра

### Ключевые компоненты

| Компонент | Описание |
|-----------|----------|
| **Public API в Rate Management Service** | Endpoint `GET /api/rates/public`, кеширование в Redis (5 мин), проксирование через Kong |
| **SFTP Rate Exporter** | Новый микросервис: подписка на Kafka `rates.updated`, генерация CSV/JSON, загрузка на SFTP (Java Spring Boot, JSch) |
| **SFTP Server** | OpenSSH или AWS Transfer Family, директория `/rates/`, SSH key auth, IP whitelist, очистка файлов > 7 дней |
| **Kong API Gateway** | Route `/api/rates/public` → Rate Management Service; плагины: API Key Auth, Rate Limiting |
| **Kafka** | Топик `rates.updated`; Producer: Rate Management Service; Consumer: SFTP Rate Exporter |

## Альтернативные решения

| Альтернатива | Плюсы | Минусы | Вердикт |
|--------------|-------|--------|---------|
| **1. Прямой доступ к БД Rate Management Service** | Простота, нет задержек | Нарушение security, tight coupling, нет rate limiting | Отклонено |
| **2. Email рассылка файлов со ставками** | Простота реализации | Низкая надёжность (спам), нет автоматизации импорта, не real-time | Отклонено |
| **3. REST API для партнёрского кол-центра** | Унифицированный подход | Партнёр не готов к API; увеличивает time-to-market | Отклонено |
| **4. WebSocket для real-time push** | Мгновенное обновление | Overkill для MVP (ставки редко меняются), сложность | Запланировать на Q4 2026 (фаза 3) |

---

## Риски и недостатки выбранного решения

| Риск | Митигация |
|------|-----------|
| Партнёр не забирает файлы с SFTP вовремя | Алерты при отсутствии заборов файлов > 30 минут |
| SFTP-сервер — single point of failure | HA режим с failover на резервный сервер |
| Утечка API-ключа | Rate limiting + мониторинг аномальной активности + ротация ключей каждые 3 месяца |
| Задержка обновления до 15 минут неприемлема | Запланировать WebSocket интеграцию на Q4 2026 |
| Рост размера файлов CSV/JSON | Компрессия (gzip) + pagination в будущем |
