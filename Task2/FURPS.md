# Задание 2: FURPS+ таблица

## Архитектурно-значимые требования для цифровизации банка "Стандарт"

| Код | Требования | Комментарий |
|-----|------------|-------------|
| **F** | **Функциональные (Functionality)** | |
| F-1 | Новый клиент на сайте может просмотреть список депозитов с актуальными ставками и подать заявку (ФИО + телефон) | Базовый функционал MVP для привлечения новых клиентов |
| F-2 | Существующий клиент в интернет-банке видит список депозитов с персонализированными ставками и может подать заявку с указанием счёта и суммы | Ключевая функция для retention существующих клиентов |
| F-3 | Подтверждение заявки на депозит/кредит через СМС-код в интернет-банке | Обязательная двухфакторная аутентификация для финансовых операций (требование ЦБ РФ) |
| F-4 | Менеджер кол-центра может просмотреть заявку нового клиента и предложить особые условия | Персонализация для повышения конверсии |
| F-5 | Менеджер бэк-офиса подтверждает условия депозита/кредита в АБС (MVP) | Основной процесс обработки заявок на MVP |
| F-6 | СМС-уведомления клиенту: после подтверждения ставки депозита, после открытия депозита, при изменении статуса заявки на кредит | Информирование клиента о статусе заявки на всех этапах |
| F-7 | Централизованное хранение и управление ставками по депозитам и кредитам (замена Excel-файлов) | **ДОБАВЛЕНО:** Сейчас ставки в Excel → высокий риск ошибок, отсутствие версионирования, сложность согласования между бэк-офисами депозитов и кредитов. Необходим Single Source of Truth |
| F-8 | Новый клиент на сайте может заполнить паспортные данные и получить мгновенное решение об одобрении/неодобрении кредита (скоринг через Бюро кредитных историй) | Мгновенное решение повышает конверсию на 20-30% (industry benchmark) |
| F-9 | Существующий клиент в интернет-банке видит предодобренные кредитные предложения на основе скоринга | Персонализация снижает время обработки заявки |
| F-10 | Сотрудник отделения может продолжить работу с заявкой на кредит, поданной клиентом на сайте (омниканальность) | Бесшовный клиентский опыт между каналами (web → офлайн) |
| F-11 | Повторный упрощённый скоринг для предодобренных кредитных заявок при изменении ситуации клиента | Актуализация данных при повторной подаче заявки |
| F-12 | API для интеграции с внешними системами: Кредитный конвейер, Система скоринга, Бюро кредитных историй, Кол-центр | **ДОБАВЛЕНО:** Необходимо для слабосвязанной архитектуры и возможности замены компонентов |
| **U** | **Удобство использования (Usability)** | |
| U-1 | Интерфейс должен быть максимально удобным для клиента (UX-тестирование перед запуском) | Повышение конверсии и удовлетворённости клиентов |
| U-2 | Соблюдение системы дизайна банка: привычные цвета, брендированные элементы, единый UI-kit | Узнаваемость бренда и консистентность между каналами |
| U-3 | Минимизация шагов для подачи заявки: для новых клиентов на депозит — только ФИО + телефон (2 поля) | **ДОБАВЛЕНО:** Снижение барьера входа для новых клиентов. Каждое дополнительное поле снижает конверсию на 5-10% |
| U-4 | Чёткая визуализация статуса заявки на всех этапах (прогресс-бар или timeline) | **ДОБАВЛЕНО:** Клиенты должны понимать, на каком этапе их заявка, это снижает количество звонков в кол-центр на 30% |
| U-5 | Адаптивный дизайн для мобильных устройств (responsive design) | **ДОБАВЛЕНО:** >60% трафика банковских сервисов приходит с мобильных устройств |
| **R** | **Надёжность (Reliability)** | |
| R-1 | Все сервисы (интернет-банк, сайт, новые сервисы) должны быть доступны 24/7 с uptime 99.9% | 99.9% = ~8.76 часов простоя в год. Критично для финансовых сервисов |
| R-2 | Резервный ЦОД для автоматического переключения в случае сбоя основного (failover) | Disaster Recovery. Текущее решение: переключение вручную → нужна автоматизация |
| R-3 | Избежать прямой синхронной интеграции интернет-банка с базой данных АБС | **КРИТИЧНО:** База АБС уже перегружена. Прямая интеграция создаёт риск остановки ядра банка при росте онлайн-нагрузки. Использовать асинхронную интеграцию через очереди сообщений |
| R-4 | Горизонтальное масштабирование интернет-банка: распределение нагрузки между несколькими серверами и ЦОД | Поддержка роста числа клиентов. Сейчас всё работает в одном ЦОД → single point of failure |
| R-5 | Механизм обработки дублирующих заявок (дедупликация) | **ДОБАВЛЕНО:** Клиент может подать заявку на сайте, потом в интернет-банке, потом в отделении. Нужно избежать создания нескольких заявок на один продукт |
| R-6 | Мониторинг состояния всех систем в реальном времени с алертами при деградации | **ДОБАВЛЕНО:** Для обеспечения 99.9% uptime нужен проактивный мониторинг (Prometheus + Grafana или аналог) |
| R-7 | Circuit Breaker для защиты от каскадных сбоев при недоступности внешних систем (АБС, скоринг, БКИ) | **ДОБАВЛЕНО:** Если система скоринга недоступна, это не должно ронять весь интернет-банк |
| **P** | **Производительность (Performance)** | |
| P-1 | Отклик по всем пользовательским операциям должен быть <500мс (целевое: <200мс) | Сейчас справочники загружаются >1 сек — это критично плохо для UX. Исследования показывают: каждая секунда задержки снижает конверсию на 7% |
| P-2 | Обработка предодобренных кредитных заявок в течение того же рабочего дня (вместо текущих раз в сутки batch-процессов) | Конкурентное преимущество — быстрое решение. Требует пересмотра интеграции АБС ↔ Кредитный конвейер |
| P-3 | Система должна выдерживать онлайн-подачу заявок на большое количество продуктов без деградации производительности АБС | **КРИТИЧНО:** Защита ядра банка от перегрузки. Пиковая нагрузка может быть в 10-20 раз выше средней (акции, рекламные кампании) |
| P-4 | Кеширование справочных данных (список депозитов, ставки, условия кредитов) на уровне API Gateway или CDN | **ДОБАВЛЕНО:** Решение проблемы с загрузкой справочников >1 сек. Справочники обновляются редко (раз в день) → можно агрессивно кешировать |
| P-5 | Не перегружать систему скоринга дополнительными предрасчётами | Система скоринга уже загружена в рабочие часы → риск деградации критичной системы |
| P-6 | Load Balancing: равномерное распределение запросов между серверами интернет-банка (Round Robin / Least Connections) | Горизонтальное масштабирование требует балансировщика нагрузки |
| P-7 | Database Connection Pooling для эффективного управления соединениями с БД | **ДОБАВЛЕНО:** Снижение нагрузки на БД и улучшение времени отклика |
| **S** | **Поддерживаемость (Supportability)** | |
| S-1 | Использовать существующие технологии банка: MS SQL, Oracle для баз данных | Снижение TCO (Total Cost of Ownership), есть экспертиза у команд |
| S-2 | Новые технологии должны быть совместимы с текущим стеком разработки (Java/.NET/Python) и инфраструктурой | Избежать технологической изоляции и vendor lock-in |
| S-3 | Внутри банка должна быть экспертиза по новым технологиям (хотя бы на уровне языков программирования) | Возможность поддержки и развития без критической зависимости от подрядчиков |
| S-4 | Для асинхронного обмена сообщениями использовать Kafka (на перспективу) | НО: текущий интернет-банк несовместим с Kafka → требуется миграция на микросервисную архитектуру или использование адаптера |
| S-5 | Постепенный переход интернет-банка на микросервисную архитектуру, начиная с модуля депозитов (Strangler Fig Pattern) | Модернизация монолита без остановки бизнеса. Новые функции реализуются как микросервисы, старые постепенно мигрируются |
| S-6 | Разработать архитектурную документацию (C4 Model: Context, Container, Component) и API-спецификации (OpenAPI/Swagger) | Knowledge transfer, onboarding новых разработчиков, согласование между командами |
| S-7 | Модульная архитектура новых сервисов для независимого развития и развёртывания | **ДОБАВЛЕНО:** Снижение зависимостей между командами, ускорение разработки |
| S-8 | CI/CD pipeline для автоматизации тестирования и развёртывания новых сервисов | **ДОБАВЛЕНО:** Ускорение выпуска новых функций, снижение human errors при деплое |
| S-9 | Логирование в централизованную систему (ELK Stack или аналог) для troubleshooting и аудита | **ДОБАВЛЕНО:** Упрощение поиска проблем в распределённой системе |
| S-10 | Версионирование API (v1, v2) для обратной совместимости при обновлениях | **ДОБАВЛЕНО:** Избежать breaking changes для существующих клиентов API |
| **+SEC** | **Безопасность (Security)** | |
| SEC-1 | Шифрование трафика TLS 1.2+ (HTTPS) на сайте и в интернет-банке для защиты чувствительной информации | **КРИТИЧНО:** Обязательное требование для финансовых организаций. Передаются ФИО, телефон, паспортные данные, финансовая информация |
| SEC-2 | Шифрование персональных данных в базах данных (encryption at rest) | **ДОБАВЛЕНО:** Защита от утечек при компрометации БД. Требование 152-ФЗ |
| SEC-3 | Двухфакторная аутентификация (2FA) через СМС-код для всех критичных операций (подача заявок на депозиты/кредиты) | Предотвращение мошенничества и несанкционированного доступа |
| SEC-4 | Разграничение прав доступа (RBAC - Role-Based Access Control): менеджеры кол-центра / бэк-офиса депозитов / бэк-офиса кредитов / администраторы | **ДОБАВЛЕНО:** Принцип наименьших привилегий (Principle of Least Privilege). Каждая роль видит только необходимые данные |
| SEC-5 | Audit Log: логирование всех операций с заявками (создание, изменение статуса, просмотр) для аудита и расследования инцидентов | **ДОБАВЛЕНО:** Compliance с требованиями ЦБ РФ (положение 382-П). Immutable log |
| SEC-6 | Хранение и обработка персональных данных в соответствии с 152-ФЗ "О персональных данных" | **КРИТИЧНО:** Обязательное требование российского законодательства. Штрафы до 75 000₽ для юр.лиц |
| SEC-7 | Rate Limiting на API Gateway для защиты от DDoS и автоматических атак | **ДОБАВЛЕНО:** Ограничение количества запросов с одного IP (например, 100 req/min) |
| SEC-8 | Input Validation и защита от SQL-injection, XSS на всех формах ввода данных | **ДОБАВЛЕНО:** Базовая защита от распространённых уязвимостей (OWASP Top 10) |
| **+R** | **Ограничения (Restrictions/Constraints)** | |
| CON-1 | База данных АБС уже перегружена → ЗАПРЕЩЕНО добавлять прямую синхронную онлайн-нагрузку | **КРИТИЧНО:** Риск остановки ядра банка. АБС обрабатывает все транзакции банка — его падение = остановка бизнеса |
| CON-2 | АБС масштабируется только вертикально (Oracle Database, монолитная архитектура) | Ограничение legacy-системы. Вертикальное масштабирование = дорого и имеет физический предел |
| CON-3 | Обмен данными между АБС и Кредитным конвейером происходит раз в сутки (batch ETL) — нельзя ускорить из-за архитектурных ограничений | Требуется обходное решение для ускорения обработки предодобренных заявок (возможно, отдельная БД-реплика для чтения) |
| CON-4 | Функционал СМС реализован в ядре системы (подрядчик) → желательно избежать доработок для снижения зависимости | Можно реализовать wrapper-сервис силами внутренней команды для управления СМС-уведомлениями |
| CON-5 | Текущая платформа интернет-банка несовместима с Kafka (legacy технологии) | Требуется либо миграция на микросервисы, либо использование промежуточного адаптера (например, REST → Kafka bridge) |
| CON-6 | Scope MVP: заявки обрабатываются только через менеджера бэк-офиса (не полностью автоматизированы) | После MVP планируется автоматизация согласования и открытия депозитов/кредитов |
| CON-7 | Новый клиент ОБЯЗАН прийти в отделение для идентификации (требование ЦБ РФ - 115-ФЗ "О противодействии легализации доходов") | **КРИТИЧНО:** Законодательное требование. Удалённая идентификация возможна только через Госуслуги (ЕСИА), но это за рамками MVP |
| CON-8 | Интернет-банк сейчас работает в одном ЦОД на одной группе серверов | **КРИТИЧНО:** Single Point of Failure. Требуется распределение нагрузки между основным и резервным ЦОД |
| CON-9 | Система скоринга перегружена в рабочие часы (9:00-18:00) → не добавлять предрасчёты скорингов в это время | Либо запускать предрасчёты ночью, либо масштабировать систему скоринга (она поддерживает горизонтальное масштабирование) |
| CON-10 | Бюджетное ограничение: использовать существующие технологии для снижения затрат на обучение и лицензии | **ДОБАВЛЕНО:** Оптимизация TCO. Новые технологии вводить только при явной необходимости |
| CON-11 | Команда разработки банка ограничена: нужно приоритизировать функции и использовать подрядчиков для типовых задач | **ДОБАВЛЕНО:** Resource constraint. Внутренняя команда фокусируется на бизнес-логике, инфраструктуру можно отдать на аутсорс |
| **+DC** | **Проектные ограничения (Design Constraints)** | |
| DC-1 | Использовать асинхронный обмен данными через очереди сообщений (Message Queue) вместо прямых синхронных вызовов к АБС | **КРИТИЧНО:** Защита АБС от перегрузки, обеспечение eventual consistency, возможность retry при сбоях |
| DC-2 | ЗАПРЕЩЕНО прямое подключение к базе данных АБС из внешних систем (интернет-банк, сайт) | Интеграция через БД — антипаттерн. Использовать API Gateway → Backend Services → АБС API |
| DC-3 | Реализовать API Gateway как единую точку входа для всех внешних запросов (от интернет-банка, сайта, мобильного приложения в будущем) | **ДОБАВЛЕНО:** Централизация security, rate limiting, routing, monitoring. Упрощает управление API |
| DC-4 | Внедрить центральное хранилище ставок (Rate Management System) с версионированием и workflow согласования | Замена Excel. Может быть реализовано как отдельный микросервис или модуль в АБС |
| DC-5 | Использовать Event-Driven Architecture для интеграции между системами (события: "Заявка создана", "Статус изменён", "Депозит открыт") | **ДОБАВЛЕНО:** Слабая связанность, масштабируемость, возможность добавления новых подписчиков на события без изменения publishers |
| DC-6 | Реализовать Strangler Fig Pattern для постепенной миграции интернет-банка: новые функции как микросервисы, старые остаются в монолите | Безопасная модернизация без остановки бизнеса. Начать с модуля депозитов, затем кредиты, платежи и т.д. |
| DC-7 | Database per Service для новых микросервисов (если используется микросервисная архитектура) | **ДОБАВЛЕНО:** Каждый микросервис имеет свою БД для обеспечения автономности и независимости развёртывания |
| **+IMP** | **Реализация (Implementation)** | |
| IMP-1 | Реализация wrapper-сервиса для СМС-уведомлений силами команды разработки банка (без доработок ядра подрядчиком) | Снижение зависимости от подрядчика, управление бизнес-логикой уведомлений |
| IMP-2 | Итеративная разработка: MVP (базовый функционал) → v1.1 (автоматизация) → v2.0 (расширение на другие продукты) | Быстрый выход на рынок, валидация гипотез, минимизация рисков |
| IMP-3 | Нагрузочное тестирование (Performance Testing) перед запуском в продакшн: симуляция пиковых нагрузок (в 20 раз выше средней) | **ДОБАВЛЕНО:** Проверка соответствия требованиям P-1, P-3. Инструменты: JMeter, Gatling, k6 |
| IMP-4 | Пилотный запуск (Soft Launch) с ограниченной аудиторией (5-10% клиентов) для валидации решения | **ДОБАВЛЕНО:** Снижение рисков, сбор обратной связи, fine-tuning перед полным запуском |
| IMP-5 | Canary Deployment для новых версий сервисов: сначала 5% трафика, потом 20%, 50%, 100% | **ДОБАВЛЕНО:** Возможность быстрого rollback при обнаружении проблем |
| IMP-6 | Использовать Feature Toggles для управления функциональностью без передеплоя | **ДОБАВЛЕНО:** Возможность включать/выключать функции на продакшне, A/B тестирование |
