## Функциональные требования

Верхнеуровневые Use Cases для открытия депозитов онлайн:

| № | Действующие лица или системы | Use Case | Описание |
|:-:|------------------------------|----------|----------|
| UC-1 | Новый клиент, Сайт банка, Менеджер кол-центра | Подача заявки на депозит с сайта | 1. Новый клиент открывает сайт банка<br>2. Клиент просматривает список депозитов с актуальными ставками<br>3. Клиент выбирает депозит и заполняет форму (ФИО + телефон)<br>4. Система сохраняет заявку<br>5. Менеджер кол-центра получает уведомление о новой заявке<br>6. Менеджер открывает заявку в системе кол-центра<br>7. Менеджер звонит клиенту и предлагает условия (возможно, особые)<br>8. Клиент приходит в отделение для идентификации и открытия депозита |
| UC-2 | Существующий клиент, Интернет-банк, Менеджер бэк-офиса | Подача заявки на депозит из интернет-банка | 1. Клиент авторизуется в интернет-банке<br>2. Клиент открывает раздел "Депозиты"<br>3. Система отображает список депозитов с персонализированными ставками<br>4. Клиент выбирает депозит и указывает счёт и сумму<br>5. Система отправляет СМС-код на телефон клиента<br>6. Клиент вводит СМС-код для подтверждения<br>7. Система сохраняет заявку и отправляет её в АБС через очередь<br>8. Менеджер бэк-офиса обрабатывает заявку в АБС<br>9. Менеджер подтверждает ставку → клиент получает СМС<br>10. Менеджер открывает депозит → клиент получает СМС |
| UC-3 | Сотрудник бэк-офиса депозитов, АБС | Управление ставками по депозитам | 1. Сотрудник открывает модуль управления ставками<br>2. Сотрудник создаёт/изменяет ставку по депозиту<br>3. Система сохраняет изменения в центральное хранилище ставок<br>4. Ставка проходит workflow согласования (если требуется)<br>5. После согласования ставка публикуется на сайте и в интернет-банке |
| UC-4 | Менеджер бэк-офиса, АБС, Клиент | Обработка заявки менеджером (MVP) | 1. Менеджер получает заявку в очереди АБС<br>2. Менеджер открывает заявку и проверяет данные<br>3. Менеджер подтверждает условия депозита (ставка, срок, сумма)<br>4. Система отправляет СМС-уведомление клиенту о подтверждении ставки<br>5. Менеджер открывает депозит в АБС<br>6. Система отправляет СМС-уведомление клиенту об открытии депозита<br>7. Система обновляет статус заявки |
| UC-5 | Сайт/Интернет-банк, Сервис ставок | Получение актуальных ставок | 1. Клиент открывает страницу депозитов<br>2. Система запрашивает актуальные ставки из сервиса ставок<br>3. Сервис ставок возвращает список депозитов с условиями<br>4. Для авторизованного клиента система запрашивает персонализированные ставки<br>5. Система отображает список депозитов с кешированием на 1 час |

## Нефункциональные требования

Архитектурно-значимые требования из FURPS+ анализа:

| № | Требование |
|:-:|------------|
| NFR-1 | **Доступность 99.9% (24/7):** Все сервисы должны быть доступны круглосуточно с максимальным временем простоя 8.76 часов в год |
| NFR-2 | **Производительность:** Отклик по всем пользовательским операциям <500мс (целевое: <200мс). Справочники должны загружаться мгновенно |
| NFR-3 | **Защита АБС:** ЗАПРЕЩЕНО прямое синхронное взаимодействие интернет-банка/сайта с базой данных АБС. Использовать асинхронную интеграцию через очереди сообщений |
| NFR-4 | **Масштабируемость:** Горизонтальное масштабирование интернет-банка и новых сервисов. АБС масштабируется только вертикально |
| NFR-5 | **Безопасность:** Шифрование трафика (TLS 1.2+), двухфакторная аутентификация (СМС-код) для критичных операций, защита персональных данных (152-ФЗ) |
| NFR-6 | **Отказоустойчивость:** Резервный ЦОД с автоматическим failover, Circuit Breaker для защиты от каскадных сбоев |
| NFR-7 | **Технологический стек:** Использовать существующие технологии банка (MS SQL, Oracle). Новые технологии должны быть совместимы |
| NFR-8 | **Поддерживаемость:** Документация (C4, OpenAPI), CI/CD pipeline, централизованное логирование |
| NFR-9 | **Кеширование:** Агрессивное кеширование справочных данных (ставки, условия) с TTL = 1 час для снижения нагрузки на backend |
| NFR-10 | **Модернизация:** Постепенный переход к микросервисной архитектуре (Strangler Fig Pattern) начиная с модуля депозитов |

## Решение

### Архитектурный подход

Для реализации MVP онлайн-открытия депозитов выбрана **гибридная архитектура**:
- **Монолитный интернет-банк** (legacy) остаётся без изменений
- **Новые микросервисы** для депозитного функционала (Rate Service, Deposit Application Service)
- **API Gateway** как единая точка входа
- **Message Queue (Kafka)** для асинхронной интеграции с АБС
- **Кеширование (Redis)** для ускорения загрузки справочников

### Обоснование ключевых решений

#### 1. API Gateway
**Зачем:** 
- Единая точка входа для сайта и интернет-банка
- Централизация security (authentication, authorization, rate limiting)
- Маршрутизация запросов к legacy и новым сервисам
- Агрегация данных из нескольких источников

**Технология:** Kong или AWS API Gateway (совместим с текущим стеком)

#### 2. Асинхронная интеграция через Kafka
**Зачем:**
- **NFR-3:** Защита АБС от перегрузки онлайн-запросами
- Eventual consistency вместо прямых транзакций
- Возможность retry при сбоях
- Event-driven architecture для расширения функционала

**Как работает:**
1. Клиент подаёт заявку в интернет-банке
2. Заявка сохраняется в БД микросервиса Deposit Application Service
3. Событие `DepositApplicationCreated` публикуется в Kafka
4. АБС Adapter подписан на это событие и сохраняет заявку в АБС через batch-процесс
5. Менеджер обрабатывает заявку в АБС
6. АБС публикует событие `DepositApplicationApproved` → клиент получает СМС

**Проблема:** Текущий интернет-банк несовместим с Kafka (CON-5)  
**Решение:** REST Proxy для Kafka, чтобы интернет-банк мог отправлять события через HTTP API

#### 3. Rate Management Service (Сервис ставок)
**Зачем:**
- **F-7:** Централизация управления ставками вместо Excel
- Версионирование ставок
- Workflow согласования (бэк-офис депозитов + кредитов)
- Персонализация ставок для клиентов

**Технология:** 
- Backend: Java Spring Boot
- БД: PostgreSQL (для новых сервисов)
- Кеш: Redis (TTL = 1 час)

#### 4. Deposit Application Service (Сервис заявок на депозиты)
**Зачем:**
- Обработка заявок от клиентов (создание, валидация, отправка в Kafka)
- Хранение статусов заявок
- Интеграция с СМС-сервисом для уведомлений

**Технология:**
- Backend: Java Spring Boot
- БД: PostgreSQL
- Message Queue: Kafka

#### 5. Redis Cache Layer
**Зачем:**
- **NFR-2:** Ускорение загрузки справочников с >1 сек до <100мс
- Снижение нагрузки на Rate Management Service
- Кеширование списка депозитов, ставок, условий

**Стратегия:** Cache-Aside Pattern с TTL = 1 час

#### 6. SMS Service Wrapper
**Зачем:**
- **CON-4:** Избежать доработок ядра системы СМС (подрядчик)
- Централизация бизнес-логики уведомлений
- Возможность замены СМС-провайдера без изменения других сервисов

**Технология:** Тонкий wrapper на Java, вызывает существующий СМС API ядра

#### 7. Multi-DC Setup
**Зачем:**
- **NFR-1, NFR-6:** Обеспечение uptime 99.9%
- Failover между ЦОД при сбоях

**Решение:**
- Active-Passive для АБС (текущее решение)
- Active-Active для новых микросервисов и интернет-банка
- Репликация БД между ЦОД (PostgreSQL Streaming Replication)

#### Диаграмма Context (Контекст)
![C4_Context_Diagram_Platform_Online_opening_deposit_mvp.png](img%2FC4_Context_Diagram_Platform_Online_opening_deposit_mvp.png)

**Описание:** Показывает систему открытия депозитов в контексте пользователей и внешних систем.

**Действующие лица:**
- **Новый клиент** — подаёт заявку через сайт
- **Существующий клиент** — подаёт заявку через интернет-банк
- **Менеджер кол-центра** — обрабатывает заявки от новых клиентов
- **Менеджер бэк-офиса** — обрабатывает заявки в АБС
- **Сотрудник бэк-офиса депозитов** — управляет ставками

**Системы:**
- **Платформа открытия депозитов** (наша система)
- **АБС** (Автоматизированная банковская система) — ядро банка
- **Система кол-центра** — для менеджеров call-центра
- **SMS Gateway** (внешний провайдер) — отправка СМС

**Интеграции:**
- Клиенты → Платформа (HTTPS)
- Платформа → АБС (Kafka + Batch API)
- Платформа → SMS Gateway (REST API)
- Менеджеры → Система кол-центра → Платформа
